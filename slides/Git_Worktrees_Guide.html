The Problem Sound familiar?

You're deep in a feature branch, files open everywhere…
Then an urgent production bug lands in your inbox. Now you have to:

  • Stash your half-done work (and hope you remember to pop it)
  • Switch branches — wait for IDE re-indexing and rebuilds
  • Fix the bug, commit, push, switch back
  • Pop stash — pray there are no merge conflicts
  • Try to remember where you left off…
Result: Lost focus, wasted time, and increased risk of mistakes.

What is a Git Worktree?

A worktree is an additional working directory linked to the same Git repository. Each checks out a different branch, has its own staging area, but shares the same commit history and object database.
📂

Separate Directories

Each worktree lives in its own folder on disk

🔗

Shared History

All worktrees share the same .git object database

🛡️

Branch Isolation

Each worktree is locked to one branch at a time

🔄

Instant Sync

Commits in one worktree are visible in all others

Essential Commands

CommandWhat It Does
git worktree add <dir> -b <branch> New worktree + new branch
git worktree add <dir> <branch> Worktree for an existing branch
git worktree list List all active worktrees
git worktree remove <dir> Remove a worktree cleanly
git worktree prune Clean up stale metadata
git worktree lock <dir> Prevent pruning a worktree
💡 A branch can only be checked out in one worktree at a time.
Reference slide. Each row reveals as a fragment. Emphasize the one-branch-per-worktree rule.

Commands in Action


# 1. Create a worktree for a new feature
$ git worktree add ../feature-login -b feature/login

# 2. See all your worktrees
$ git worktree list

# 3. Switch context — just cd!
$ cd ../feature-login

# 4. When you're done, remove it
$ git worktree remove ../feature-login

# 5. Clean up any stale references
$ git worktree prune
That's it. No stashing. No re-cloning. Just add, cd, and remove.

Workflow: The Hotfix Scenario

1
You're working on a feature
cd ~/repo  # on branch feature/dashboard
2
Urgent bug report arrives! 🚨
# No need to stash or commit anything
3
Spin up a hotfix worktree
git worktree add ../hotfix -b hotfix/critical
4
Fix the bug in isolation
cd ../hotfix && vim src/api.js  # fix & commit
5
Push & return to your feature
git push && cd ~/repo  # right where you left off
6
Clean up when done
git worktree remove ../hotfix
Your feature branch stays untouched the entire time. Zero context loss. ✨

Worktree vs Stash vs Clone

git worktree git stash git clone
Disk Usage Low Minimal High (full copy)
Active Branches Multiple parallel One at a time Multiple (separate)
Context Loss None Possible None
Setup Cost Low (add/cd) Low (stash/pop) High (clone/setup)
Shared History Yes Yes No (independent)
IDE Windows Multiple One Multiple
Best For Parallel dev Quick switches Full isolation
Worktrees combine the best of both worlds — parallel branches with minimal overhead.

Best Practices

📁Organize Worktree Directories

Keep worktrees as siblings: workspace/repo/   workspace/feature-x/   workspace/hotfix/

🏷️Use Descriptive Names

Name directories after branches: feature-login, hotfix-api-crash

🧹Clean Up After Yourself

Always git worktree remove — don't just delete folders. Run prune periodically.

🔒Lock Important Worktrees

Use git worktree lock for long-lived worktrees to prevent accidental pruning.

📋Monitor with git worktree list

Regularly check active worktrees to avoid orphaned directories.

Operational excellence. These tips prevent the most common mistakes with worktrees.

Common Pitfalls to Avoid

⚠️ Same Branch in Two Worktrees

Git won't allow the same branch in multiple worktrees. Use -b to create a new branch.

⚠️ Deleting Folders Manually

Don't rm -rf a worktree! Always use git worktree remove, or run prune afterward.

⚠️ Forgetting About Worktrees

Orphaned worktrees waste disk space. Run git worktree list regularly.

⚠️ Submodule Complications

Submodules need manual init in each worktree: git submodule update --init

💡 Use shell aliases for common worktree operations to build muscle memory.

Key Takeaways

  1. Git worktrees let you work on multiple branches in parallel — each in its own directory.
  2. They share one .git database, making them far more efficient than multiple clones.
  3. Worktrees eliminate the need for stashing and reduce context-switching friction.
  4. Use them for hotfixes, code reviews, parallel features, and multi-version testing.
  5. Always clean up: git worktree remove when done, git worktree prune periodically.
Start small: next time you need a hotfix, reach for git worktree add instead of git stash.

Cleanup & Maintenance


# Remove a worktree cleanly
git worktree remove <dir>

# Clean stale metadata
git worktree prune

# Protect from pruning
git worktree lock <dir>

# Allow pruning again
git worktree unlock <dir>
